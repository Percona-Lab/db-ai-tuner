# Chunk 3 (durability, replication, cluster, concurrency): most useful findings

1. Binlog commit cost is the biggest uncollected signal: add performance_schema `file_summary_by_event_name` for `wait/io/file/sql/binlog` (COUNT_MISC/SUM_TIMER_MISC = fsync count/time; SUM_NUMBER_OF_BYTES_WRITE = binlog bytes). It drives sync_binlog, binlog_group_commit_sync_delay, disable_log_bin/skip_log_bin, binlog_row_image, binlog_format and binlog_transaction_compression. The tuner today collects file I/O only by InnoDB file type.
2. MariaDB group commit is already measurable from status deltas: Binlog_commits/Binlog_group_commits gives the average group size, and Binlog_group_commit_trigger_count/_timeout/_lock_wait show why each group closed. Together these decide binlog_commit_wait_count/usec.
3. On MySQL, groups that fail to form show up as waits on `MYSQL_BIN_LOG::LOCK_sync` / `COND_done` in the performance_schema wait summaries. Capture these explicitly, because they may not make the top-N list.
4. innodb_flush_log_at_trx_commit and innodb_doublewrite (high impact) are already fully covered by the eBPF redo-flush share, Innodb_os_log_fsyncs, Innodb_dblwr_* and dblwr file I/O.
5. innodb_adaptive_hash_index (medium, either direction): MariaDB exposes Innodb_adaptive_hash_hash_searches/_non_hash_searches as status variables. MySQL needs INNODB_METRICS `adaptive_hash_searches`/`adaptive_hash_searches_btree` plus the `btr_search_latch` wait, which are not collected yet. The CPU profile B-tree share is the main "enable" signal.
6. Spin and latch knobs (innodb_spin_wait_delay, sync_spin_loops, sync_array_size, thread_concurrency) are low impact. Their missing signals are INNODB_METRICS `innodb_rwlock_*_spin_rounds/os_waits` and the SEMAPHORES and ROW OPERATIONS queue lines of SHOW ENGINE INNODB STATUS.
7. innodb_deadlock_detect: add INNODB_METRICS `lock_deadlock_rounds`/`lock_deadlocks` for MySQL; MariaDB has Innodb_deadlocks. Gains appear only with hot-row pile-ups, where detection shows in the CPU profile.
8. innodb_autoinc_lock_mode: AUTO-INC table-lock waits are visible only via `performance_schema.data_lock_waits`/`data_locks` (LOCK_MODE='AUTO_INC'), which is not sampled. This matters for concurrent bulk inserts on MariaDB, where the default is 1.
9. Replication applier knobs (replica_parallel_workers, replica_preserve_commit_order, slave_parallel_*) and Galera knobs (wsrep_*_threads, wsrep_provider_options) have high impact but need replica- or cluster-side collection: replication_applier_status_by_worker timestamps, worker stage events, wsrep_flow_control_paused and wsrep_local_recv_queue_avg. A single-server benchmark cannot show them.
10. These variables are inert or have no effect, so skip them: binlog_max_flush_queue_time (documented no effect), metadata_locks_hash_instances (MariaDB: unused), sync_relay_log_info (table repositories), pxc_strict_mode (not performance), innodb_rollback_segments (default 128 is already the maximum).
